# Поиск Slot Fingerprint — на чистом Python через байтовые таблицы и «полосы» в больших целых

Перед каждым Mouse Click движок сверяет Slot Fingerprint. Если ячейка не на месте, он ищет её в радиусе `fingerprint_search_radius` (150 пикс.) вокруг точки. Поиск на обычных циклах Python по пикселям на живом LU4 занимал 0,8–2,4 с на одну проверку (2026-10-05, `probe/perf_fingerprint.py`). Он шёл под блокировкой движка, которую ждал и поток интерфейса, поэтому при трёх действиях с пропавшими ячейками программа зависала, а Windows помечала её как «не отвечает».

Решение: попиксельная работа выполняется внутри C, но без сторонних библиотек (`myclicker/domain/pixels.py`):

- `bytes.translate` с таблицей на 256 значений за один вызов превращает целую плоскость канала в |значение − v|;
- байты, разнесённые по 16-битным «полосам» и прочитанные как одно большое целое, складываются, вычитаются и маскируются все сразу (SWAR). Значения подобраны так, чтобы полосы не переполнялись друг в друга.

Это дало 140–830 мс вместо 1,8–5,2 с на одном и том же кадре игры, с теми же найденными точками. Сам снимок окна (`PrintWindow`) стоит ещё около 50 мс. Тест `tests/test_fingerprint_perf.py` держит бюджет 0,6 с на проверку (с запасом на загруженный компьютер: сборка без зелёных тестов не идёт).

## Почему не numpy

numpy сделал бы то же короче и быстрее. Но программа переносная и работает без сторонних библиотек (AGENTS.md), а numpy в exe прибавляет десятки мегабайт. Если когда-нибудь numpy появится в зависимостях, `pixels.py` можно заменить, не меняя `FingerprintMatcher`.

## Consequences

- Код в `pixels.py` читается хуже обычных циклов. Каждая функция объясняет, почему полосы не переполняются. Менять её стоит вместе с тестами `test_fingerprint*.py`.
- Отпечаток ячейки сравнивается сначала на месте, потом поиском, и всё это по одному снимку окна.
- Пока ячейка не находится, движок ищет её всё реже: через 1, 2, 4, 8 с, дальше раз в 8 с. После удачной проверки снова каждую секунду.
